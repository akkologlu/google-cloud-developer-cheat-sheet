# Handbook Principles

> "The purpose of this handbook is not to document Google Cloud.
> The purpose is to help developers truly understand it."

---

# Why This Handbook Exists

Google Cloud already has excellent official documentation.

This repository is **not** another copy of that documentation.

Instead, it aims to answer the questions that developers often have after reading the docs.

Questions like:

- Why does this service exist?
- What problem does it solve?
- How does it fit into the Google Cloud ecosystem?
- When should I choose it over another service?
- How would I use it in a real project?

---

# Our Mission

Build a handbook that helps software engineers think like cloud architects.

The goal is understanding.

Certification success should be a consequence—not the primary objective.

---

# Core Principles

## 1. Understand Before Memorizing

Memorizing service names is temporary.

Understanding why services exist is permanent.

Every chapter should explain the motivation behind a service before describing its features.

---

## 2. Explain the Problem Before the Solution

Every Google Cloud service exists because it solves a specific problem.

Always introduce the problem first.

Only then introduce the service.

---

## 3. Teach Like a Senior Engineer

Assume the reader is an experienced software developer who is new to Google Cloud.

Avoid unnecessary jargon.

Explain concepts clearly.

Use practical examples.

---

## 4. Focus on Real-World Software Development

Cloud services rarely exist in isolation.

Explain how services work together.

Use realistic architectures whenever possible.

Examples are more valuable than definitions.

---

## 5. Build Mental Models

Readers should finish each chapter with a mental model—not just a list of features.

Good mental models are remembered long after technical details fade.

---

## 6. Compare Services

Understanding comes from comparison.

Whenever appropriate, compare services that solve similar problems.

Examples include:

- Cloud Run vs GKE
- Cloud SQL vs Spanner
- Firestore vs Bigtable
- Pub/Sub vs Cloud Tasks

Explain not only the differences, but also **why** those differences matter.

---

## 7. Visualize Everything

Architecture diagrams are often easier to understand than paragraphs.

Whenever possible, use:

- Mermaid diagrams
- Tables
- Flowcharts
- Architecture sketches

---

## 8. Keep It Developer-Focused

This handbook is written for developers.

Whenever discussing infrastructure, always connect it back to software development.

Readers should constantly understand:

> "How does this help me build better software?"

---

## 9. Optimize for Long-Term Learning

Avoid writing content that is useful only for passing an exam.

Instead, write content that will still be valuable years later.

---

## 10. Pursue Technical Excellence

Every page should meet the following standard:

> "Would I confidently recommend this page to another software engineer?"

If the answer is "no," improve it before publishing.

---

# Writing Philosophy

Every chapter should answer four fundamental questions:

1. Why does it exist?
2. How does it work?
3. When should I use it?
4. What are the alternatives?

If a chapter fails to answer any of these questions, it is incomplete.

---

# Success Criteria

A successful chapter enables the reader to:

- Explain the service in their own words.
- Select the appropriate service for a given problem.
- Understand the trade-offs.
- Apply the knowledge in a real project.
- Feel prepared for certification questions.

---

# Long-Term Vision

This handbook aims to become a trusted learning resource for developers exploring Google Cloud.

The measure of success is simple:

A reader should leave each chapter with a deeper understanding—not just more information.

---
